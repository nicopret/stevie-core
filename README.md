# Stevie

Stevie is an event-driven media orchestration platform designed to provide a unified interface for televisions, streaming services, media devices, and smart home integrations.

Rather than individual clients communicating directly with hardware or online services, every interaction flows through Stevie's kernel, event bus, and telemetry pipeline.

```
        ┌──────────────────┼──────────────────┐
        │                  │                  │
 Configuration      Device Registry      Event Bus
        │                  │                  │
        └──────────────────┼──────────────────┘
                           │
                       Telemetry
                           │
                     Device Services
                           │
                    Samsung TV Service
```

## Design Principles

* Event-driven architecture
* Fully asynchronous (`asyncio`)
* Service/component based
* Transport independent
* Extensible through drivers and integrations
* Strongly typed identifiers using `StrEnum`
* Structured telemetry pipeline
* Designed for Home Assistant, mobile applications, CAN bus and custom hardware

# Current Components

## Devices and Device Registry

`Device` retains Explorer's `id`, `device_name`, `display_name`, `ip_address`,
targets, and vendor authentication. `DeviceTarget` describes each target using
`target_id`, `name`, and `display_name`. IDs are supplied by Explorer and never
generated by Core. Authentication is excluded from model representations and
serialization, but remains available internally.

`DeviceRegistry` is a synchronous kernel component, available through
`kernel.get(ServiceName.DEVICE_REGISTRY)`. It offers `load()`, `get(id)`, `has(id)`,
`all()`, `find_by_name(name)`, `get_target(device_id, target_id)`, and `reload()`.
Unknown device or target IDs raise `KeyError`.

Set `DEVICES_FILE` to the configuration file path (default `data/devices.json`).
Core accepts Explorer's current `{"version": 0, "devices": [...]}` document as
well as a plain device list. Missing files mean an empty registry; invalid JSON,
invalid records, and duplicate device IDs or target IDs within a device fail
loading. Core never creates or writes this file: Explorer owns discovery and
updates. Point `DEVICES_FILE` at Explorer's file when sharing configuration.
Absolute paths are used directly; relative paths are relative to Core's working
directory. Explorer does not need to be running: Core makes no API calls to it.

Core does not watch the file. Explorer changes become visible only after an
explicit `registry.reload()` or a restart. Reload validates the complete new
state before replacing the registry, preserving supplied IDs even when IPs,
labels, or targets change. Any failed reload (including a missing or unreadable
file) raises an error and retains the last valid state. A valid empty device
list intentionally empties the registry.

Core currently reads only the target identity/name fields; additional Explorer
transport metadata is ignored. IDs and IP addresses remain strings, and vendor
authentication is a flexible mapping (or `null`). Registry loading currently
emits no telemetry. At startup, Core creates a Samsung service for every Device
exposing `samsung.remote.control`, using its IP and Explorer-owned authentication.
Registry reload does not recreate or update running services; restart Core to
apply changed configuration to those services.

## HTTP API

Core exposes a FastAPI API at `http://localhost:8000/api/v1`.
Set `API_HOST` (default `0.0.0.0`) and `API_PORT` (default `8000`) to configure
its listener. Swagger UI is at `/docs`; the generated schema is at `/openapi.json`.

* `GET /api/v1/health` — API liveness, without checking physical devices.
* `GET /api/v1/components` — registered component names and types only.
* `GET /api/v1/devices` — current registry devices and target identities.
* `GET /api/v1/devices/{device_id}` — one device, or HTTP 404.

Public device schemas exclude authentication and credentials. Thin routes share
Core's existing kernel and registry; they do not discover or modify devices.
API authentication is not implemented in this phase.

The kernel starts the API after device services and stops it first. Uvicorn runs
in the same asyncio process, with its signal-capture hook disabled so the kernel
owns SIGINT/SIGTERM. Existing typed kernel lifecycle telemetry covers the API
service. Startup failures retain the kernel's rollback policy; a failed TV can
therefore prevent API startup. A missing devices file permits device-less startup.

Run `uv run python -m stevie.main` to start Core. Registry reload affects device
read responses, but does not reconcile running device services.

## Device commands

* `GET /api/v1/devices/{device_id}/commands` lists the active controller's
  implemented commands without contacting the physical device.
* `POST /api/v1/devices/{device_id}/commands` executes one logical command and
  waits for it to be sent. A successful response contains `device_id`, `command`,
  `status: "completed"`, and `result: null`; it does not confirm the TV acted on it.

Example POST bodies:

```json
{"command": "remote.home"}
```
```json
{"command": "audio.volume_up"}
```
```json
{"command": "remote.key", "arguments": {"key": "KEY_GUIDE"}}
```
```json
{"command": "channel.select", "arguments": {"channel": 101}}
```

The initial vocabulary is `remote.key`, `remote.home`, `remote.back`,
`audio.volume_up`, `audio.volume_down`, `audio.mute`, `channel.up`, `channel.down`,
and `channel.select`. The Samsung controller translates these into its existing
remote methods. `remote.key` accepts only keys from the local catalogue matching
Explorer; power keys and raw payloads are excluded. `channel.select` requires a
nonnegative integer (not a boolean or numeric string). Extra arguments are rejected.

The `DeviceCommandService` component maps stable device IDs to existing runtime
controllers during application composition. API callers do not use runtime service
names. No new connection is created by a command request. Known devices without a
controller or with unavailable transport return 503; unknown devices return 404,
unknown commands 400, unsupported commands or invalid arguments 422, and unexpected
execution failures 500. Error responses omit raw exceptions and submitted values.

Successful execution publishes `device.command.completed`. Typed started,
completed, and failed telemetry contains only device ID and command, not arguments
or authentication. The catalogue describes Core implementation support, not
Explorer-verified physical-device capabilities. Capability filtering, queues,
retries, batching, and power commands remain outside this implementation.

## Samsung TV

Current capabilities:

* Secure WebSocket connection
* Explorer-provided authentication
* Remote key presses
* Channel selection
* Event publishing
* Telemetry integration

`SamsungTVService(kernel, device, app_name="Stevie")` requires a Device with a
`samsung.remote.control` target and a nonempty `authentication.samsung.token`.
Pair devices through Stevie-Explorer before starting Core. Core neither writes
device configuration nor maintains a separate token file. `SAMSUNG_TV_IP` and
`SAMSUNG_TV_TOKEN_FILE` are no longer settings; configure `DEVICES_FILE` instead.

Instances are registered as `samsung_tv:<device_id>`, allowing multiple TVs,
including TVs with the same model or display name. Connection events and Samsung
telemetry include `device_id`, `display_name`, and `ip`, without credentials.
The kernel's existing failure policy remains: a failed service startup rolls
back previously started services. Device-failure isolation is future work.

# Development

## Requirements

* Python 3.13+
* uv
* Raspberry Pi OS Lite (recommended)

Install dependencies:

```bash
uv sync
```

Create your environment file:

```bash
cp .env.example .env
```

Run Stevie:

```bash
uv run python -m stevie.main
```

## Tests

Run the automated suite with the development dependencies installed by `uv sync`:

```bash
uv run pytest
```

Tests isolate environment settings and runtime files in temporary directories,
block real network connections, and mock the Samsung WebSocket transport. No TV,
local `.env`, or existing pairing token is required.

# Philosophy

Stevie is designed around one central idea:

> Every client communicates with Stevie.
>
> Stevie communicates with the devices.

This allows multiple front-ends—including Home Assistant, mobile applications, dashboards, CAN bus devices, and dedicated hardware—to share the same services, event model, and automation logic without duplicating functionality.
